# Docs Site Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Stand up a public mkdocs site under `site/` and deploy it to GitHub Pages via GitHub Actions on every push to `main`.

**Architecture:** A self-contained `site/` folder holds `mkdocs.yml` and four markdown pages, built with `mkdocs` + `mkdocs-material` from the root uv workspace's dev dependency group. A `.github/workflows/docs.yml` workflow builds the site with `uv` and deploys the build output via `actions/deploy-pages`. `docs/superpowers/` is untouched by any of this — mkdocs never reads outside `site/docs/`.

**Tech Stack:** mkdocs, mkdocs-material, uv (dependency groups + `uv run`), poethepoet (`poe` tasks), GitHub Actions (`actions/configure-pages`, `actions/upload-pages-artifact`, `actions/deploy-pages`).

**Spec:** `docs/superpowers/specs/2026-08-29-docs-site-design.md`

## Global Constraints

- mkdocs source lives under `site/` (`site/mkdocs.yml`, `site/docs/*.md`) — never under `docs/`, which is reserved for `docs/superpowers/` specs and plans.
- mkdocs and mkdocs-material are added to the root `pyproject.toml`'s `[dependency-groups].dev`, sharing the existing workspace lockfile — no second virtualenv, no `site/pyproject.toml`.
- Theme is `mkdocs-material`.
- No league name, league id, player data, or anything from `captured/`, `.env`, or `kb/league/` may appear in `site/docs/` — this content is published publicly.
- The build must pass `mkdocs build --strict` — that is the sole correctness gate for this project (no markdown unit tests).
- The GitHub Actions workflow triggers on `push` to `main` with a `site/**` path filter, plus `workflow_dispatch`; it needs `permissions: pages: write, id-token: write` and a `pages` concurrency group with `cancel-in-progress: false`.
- Enabling GitHub Pages itself (Settings → Pages → Source: GitHub Actions) is a manual, one-time change to real repo settings and is explicitly **out of scope** for any task below — it is called out at the end of the plan instead.

# Two suites, two rootdirs: each package keeps its own pytest configuration

test-mcp = "pytest mcp/fantacalcio/tests -c mcp/fantacalcio/pyproject.toml -q"

`-d _build` fixes the build output directory explicitly. Both `docs_dir`
and `site_dir` — including a `-d`-overridden one — resolve relative to
`mkdocs.yml`'s own directory (`site/`), not the current working directory,
so `-d _build` lands at `site/_build/`. (`-d site/_build` would double up
to `site/site/_build/` — verified by running the build.)

A Fantacalcio **Mantra** assistant: it builds and maintains a knowledge base of
Serie A clubs and players, values them ahead of an auction, and helps run a live

fantaclaude is not a general fantasy-football tool — it is built against a

- [ ] **Step 3: Write `site/docs/architecture.md`**

```markdown
# Architecture

## A two-package uv workspace

fantaclaude is a [uv workspace](https://docs.astral.sh/uv/concepts/projects/workspaces/)
with two packages sharing one lockfile and one virtual environment:

| Package | Import name | Responsibility |
| --- | --- | --- |
| `core/` | `fantaclaude` | The assistant itself: data spine, ingestion, knowledge base, CLI |
| `mcp/fantacalcio/` | `fantacalcio_mcp` | A read-only MCP server over the league's live API |

`fantaclaude` depends on `fantacalcio-mcp` as a library — it calls the API client
directly rather than going through a second network hop, so there is exactly one
copy of "what the league API looks like" in the codebase.

## The data spine

League data — the player list ("listone"), statistics, and knowledge-base facts —
is ingested from a handful of sources (the league API, public web stats, manually
curated club notes) into a local store, rather than queried live on every
question. This keeps day-to-day questions ("who scored last week?", "what's this
player's role?") fast and offline, and keeps a record of what was known and when.

## League configuration is data, not constants

A league's rules — how many participants, the budget, which formations are legal,
how scoring works — are **mutable**: they can change between seasons and even
mid-season. Nothing in fantaclaude hardcodes them. They are ingested, versioned,
and read at run time exactly like player statistics, because every valuation
depends on the rules that were in force when it was computed.
```

- [ ] **Step 4: Write `site/docs/cli.md`**

```markdown
# The `fantaclaude` CLI

The `fantaclaude` command wraps the assistant's day-to-day, non-conversational
work: pulling data in, building the knowledge base. Three groups of commands:

## `fantaclaude sync-league`

Pulls the current state of the league — settings, roster composition rules,
teams — from the live league API into the local data spine.

## `fantaclaude ingest`

Brings outside data into the data spine: the player list from the league API,
and statistics and advanced metrics from public web sources. Web ingestion is
deliberately polite — one request at a time, paced, no retries — because it reads
hosts fantaclaude doesn't control.

## `fantaclaude kb`

Builds and maintains the knowledge base under `kb/`: one rules document plus one
profile per Serie A club, refreshed as clubs change coach, formation, or European
competition status.

Each command only touches the network when it says so in its name —
`sync-league` and `ingest` call live services; everything else in the CLI works
against data already on disk.
```

- [ ] **Step 5: Write `site/docs/mcp.md`**

```markdown
# The `fantacalcio-mcp` server

`fantacalcio-mcp` is a small [MCP](https://modelcontextprotocol.io) server that
gives an LLM read-only access to a Leghe Fantacalcio.it league: account details,
league settings, team rosters, and the competitions on offer. It talks to the
league's API over stdio and exposes it as a set of typed tools rather than as
raw HTTP.

It is deliberately narrow: no writes, no auction actions, nothing that could
change league state. Its only job is answering "what does the league API say
right now?" so that both a conversational assistant and fantaclaude's own
ingestion code can ask that question without duplicating the API client.

`fantaclaude` depends on it as an ordinary Python library — `core/`'s ingestion
code imports `fantacalcio_mcp.api` directly rather than spawning the MCP server
and talking to it over stdio, so there is exactly one implementation of "what
the league API looks like" in this codebase.
```

- [ ] **Step 2: Write the workflow**

```yaml
name: docs

on:
  push:
    branches: [main]
    paths: ["site/**"]
  workflow_dispatch:

permissions:
  contents: read
  pages: write
  id-token: write

concurrency:
  group: pages
  cancel-in-progress: false

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: astral-sh/setup-uv@v3
      - run: uv sync --group dev
      - run: uv run poe docs-build
      - uses: actions/configure-pages@v5
      - uses: actions/upload-pages-artifact@v3
        with:
          path: site/_build

  deploy:
    needs: build
    runs-on: ubuntu-latest
    environment:
      name: github-pages
      url: ${{ steps.deployment.outputs.page_url }}
    steps:
      - id: deployment
        uses: actions/deploy-pages@v4
```
